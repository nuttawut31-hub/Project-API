# แบบออกแบบสถาปัตยกรรม — สัปดาห์ที่ 13

## ระบบที่ส่งจริง

Gym API ที่ส่งเป็น Express แอปเดียว (`backend/src/index.js`) ใช้ MySQL เดียว (`backend/db.js`) และหน้าเว็บ static (`frontend/`) ทำงานบน origin เดียวกัน โครงสร้างนี้เหมาะกับขนาดงานและสาธิต flow ได้ครบ ยังไม่ได้แยกบริการ deploy จริง

```text
Browser /app → Express API → MySQL
                    │
                    └→ Open-Meteo (timeout, retry, fallback)
```

## ขอบเขตบริการหากระบบเติบโต

| ขอบเขต | ข้อมูลที่รับผิดชอบ | ตัวอย่าง API | เหตุผล |
| --- | --- | --- | --- |
| Identity | users, role, login | `/api/auth/*` | กำหนดสิทธิ์การเขียนข้อมูลจากจุดเดียว |
| Branch | gyms | `/api/gyms/*` | ข้อมูลสาขาและราคาเปลี่ยนแยกจากสมาชิก |
| Member | members | `/api/members/*` | ข้อมูลส่วนบุคคลและการลงทะเบียน |
| Subscription | memberships | `/api/memberships/*` | ความสัมพันธ์สมาชิก–สาขาและสถานะ |
| Weather adapter | ผล Open-Meteo | `/api/weather` | ความล้มเหลวของบริการภายนอกไม่ควรขัดงานหลัก |

หากแยกจริง ให้ Gateway ตรวจ token ก่อนส่งต่อ คำสั่งสมัครแพ็กเกจต้องยืนยัน `member_id` และ `gym_id` ผ่าน API เจ้าของข้อมูล หรือใช้ event/read model ที่มีการซิงก์ เพราะ foreign key ข้ามฐานข้อมูลใช้ไม่ได้ ข้อมูลที่อาจล้าสมัยต้องระบุวิธีคืนค่า 404/409 และ retry อย่างชัดเจน

## ข้อดี ข้อแลกเปลี่ยน และลำดับพัฒนา

การแยกบริการทำให้ขยายเฉพาะส่วนที่โหลดสูงและ deploy แยกได้ แต่เพิ่มการสื่อสารผ่านเครือข่าย การจัดการข้อมูลข้ามบริการ การติดตาม request และต้นทุนปฏิบัติการ สำหรับงานระยะที่ 3 จึงคงระบบรวมไว้ก่อน หากมีผู้ใช้จริงมากขึ้น ให้เก็บ metrics ของเวลาตอบกลับ/จำนวนคำขอ แล้วค่อยตัดบริการที่มีเหตุผลด้านโหลดหรือทีมงานชัดเจน

เอกสารนี้เป็นโจทย์ออกแบบจากบทเรียนสัปดาห์ที่ 13 ไม่ใช่คำกล่าวว่ามี microservices หรือระบบ scale ที่ติดตั้งแล้ว
